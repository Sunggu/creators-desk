## 1. 제품 정의

범용적인 집필 지원 도구. 사람이 쓴다. 도구는 **방해하지 않고**, 정확히는 **직접 지시가 있을 때만** 도움을 준다.

집필 여부와 무관하게 붙는다 — 소설, 기술 글, 조사 노트.

## 2. 확정된 결정

| 항목 | 결정 | 비고 |
|---|---|---|
| 권위 저장소 | **클라우드** | 로컬이 아니라 서버가 진실 |
| 오프라인 | 지원한다 | 단, 편집 범위는 미정 (8. 참조) |
| 배포 형태 | **설치형 PWA** (크롬 설치) | 로컬 앱 아님. 네이티브 셸 아님 |
| 확장 | **크롬 익스텐션** | 웹 클리핑 / 퇴고용 |
| AI | **최소화.** 붙으면 좋지만 없어도 성립 | 4. 참조 |

## 3. 핵심 상호작용 모델

도구의 정체성은 두 표면의 조합이다. 두 표면은 트리거와 수명이 근본적으로 다르다.

### 3.1 코드 리뷰의 후속 코멘트 (주 표면)

- 사람이 **요청**한다. 도구가 먼저 말을 걸지 않는다.
- 지적은 **문서 내 특정 텍스트 구간에 앵커**되어 붙는다.
- 닫거나 상태를 바꿀 때까지 **남아 있다**. 무시해도 문서는 손상되지 않는다.
- 링크: `Finding` 엔티티 = 앵커 + 본문 + 심각도 + 상태(미처리/해결/무시)

### 3.2 하단 인텔리센스 고스트 텍스트 (보조 표면)

- 커서 위치에서만 나타난다.
- 즉시 사라진다. 지속되지 않는다.
- **적극적으로 뜨지 않는다.** 계속 뜨는 것을 명시적으로 거부했다.

### 3.3 그 사이의 원칙

> 도구는 "무엇을 지적할지"를 판단하지 않는다.
> 도구는 **"언제 지적할 것인지"만** 판단하고, 지적 내용은 원본에서 온다.

이 원칙이 4절의 AI 정책을 가능하게 만든다.

## 4. AI 정책

**도구는 AI 없이 완성되어야 하고, AI가 붙으면 확장되어야 한다.**

- 도구의 책임 = 언제 지적할 것인가 (트리거·앵커링·상태관리·UI)
- 지적 "내용"을 채우는 것 = pluggable backend 여러 개 중 하나
- 백엔드 교체해도 UI·트리거 코드는 불변
- AI가 붙는 지점은 "내용 생성" 한 곳으로 국한한다. 그 밖의 어떤 지점에도 AI가 스며들지 않게 한다

이 구조는 Novel-OS의 결정론적 정합성 체크(LLM 없이 즉시 도는 규칙 12종)를 AI 백엔드와 나란히 두는 방식으로, 이미 검증된 설계다.

## 5. 플랫폼 아키텍처

하나의 API를 **세 종류의 클라이언트**가 공유한다.

```
                 ┌─────────────────────────┐
                 │   Creators Desk API     │  ← 도메인 모델이 중심
                 │   (클라우드 권위)         │
                 └──────────┬──────────────┘
        ┌───────────────────┼───────────────────┐
   ┌────┴─────┐      ┌──────┴───────┐    ┌──────┴──────┐
   │  PWA 앱   │      │ 크롬 익스텐션  │    │ (추후) 데스크톱/모바일 │
   │  오프라인  │      │  클리핑/퇴고   │    └─────────────┘
   └──────────┘      └──────────────┘
```

- API는 버전이 있는 진짜 API여야 한다. 도메인 모델이 경계에 있다.
- 클라이언트 수 ≥ 2이므로 `AGENTS.md`의 포트/어댑터 구조가 실제로 값을 갖는다. 백엔드 교체는 Infrastructure 어댑터 교체 한 일이 된다.
- **익스텐션 인증**: 앱의 세션 토큰을 그대로 재사용하지 않는다. 앱을 통해 별도 디바이스 토큰을 발급받는 흐름을 쓴다.

## 6. 도메인 모델 초안

```
Document ──── 시점(Passage) ──── Finding (지적, 앵커 보유)
                                      │
                                      └─ Clipping (확장 수집물)
```

핵심 아이디어: **Finding의 앵커를 두 대상이 공유한다.**

| 앵커 종류 | 대상 | 앵커 기준 |
|---|---|---|
| 문서 내 구간 | 직접 쓴 글 | `documentId` + quoted text |
| 웹 구간 | 남의 글 | `url` + quoted text + selector |

클립퍼가 만드는 `Clipping`은 사실 "남의 글에 붙은 Finding"이다. 그래서 앵커 모델 하나, 바깥 인터페이스 두 개로 정리된다. UI가 두 개로 갈라져도 도메인은 하나다.

### 6.1 앵커는 좌표가 아니라 인용으로

**Finding은 문자 오프셋으로 앵커하지 않는다. 인용문 + 주변 맥락으로 앵커한다.**

- 앞절에서 고친 문장이 있어도 지적이 본문에서 떨어지지 않는다
- W3C Web Annotation의 `TextQuoteSelector` + `TextPositionSelector` 조합이 표준 답
- 비용: 앵커 하나가 두 필드 이상. 이게 유일한 대가

## 7. 확장 경로

범용 도구라는 목표는 다음을 **언제든 붙일 수 있어야** 한다는 뜻이다. 로드맵에 없는 기능은 목록이 아니라 확장 지점으로 취급한다.

- 데이터는 모두 클라우드에 있으므로 새 표면(데스크톱/모바일)은 API만 소비하면 된다
- AI는 backend 교체로 추가된다 (4절)
- 규칙 체크는 새 use case 추가 + Finding 생성으로 표현된다. UI 수정 불필요
- 클립퍼는 익스텐션 배포만으로 개선된다 (앱 재배포 없이)

## 8. 열린 결정 (비용이 큰 갈림길)

구현 전에 정해야 하는 것들. **1번이 유일하게 되돌리기 어려운 결정**이다.

### 8.1 오프라인 편집 범위 — 가장 비싼 갈림길

클라우드가 진실인데 오프라인에서 편집한다면, 충돌 난다.

| | 범위 | 비용 |
|---|---|---|
| **A** | 오프라인에서 **열람 + 임시 초안** 작성, 재접속 시 합류 | 낮음. 충돌 = 사용자 선택 |
| **B** | 오프라인에서 **완전 편집 + 자동 병합** | 높음. CRDT(Yjs, MIT) 필요 |

B를 고르면 도구 전반이 CRDT에 종속돼. A는 사흘, B는 기본 아키텍처가 바뀐다.

### 8.2 백엔드 선택 (미정)

`PocketBase`(MIT, 단일 바이너리, SQLite 내장) / 직접 Node 서버 + DB / BaaS. 모두 Infrastructure 어댑터 뒤에 숨길 수 있어서 뒤로 미룰 수 있다.

### 8.3 도메인 저장 단위

파일(마크다운 + frontmatter) vs DB 행. 클라우드 권위가므로 **DB 행 쪽으로 기울고 있다.** 로컬 마크다운 내보내기를 보존 기능으로 두는 형태.

## 9. 하지 않을 것

- AI가 글을 대신 쓰지 않는다
- AI가 스스로 먼저 말을 걸지 않는다
- 지속적으로 떠 있는 제안 UI를 만들지 않는다
- 네이티브 데스크톱 앱(설치·코드사인·플랫폼 빌드)을 만들지 않는다 — PWA가 그 자리를 대체한다
- 노트/태그/백링크 중심의 범용 PKM으로 방향을 바꾸지 않는다

## 10. README와의 불일치 (미해결)

`README.md`는 현 시점 "로어 관리 + 멀티 프로젝트 파이프라인 조율"을 내세운다. 이는 이 로드맵의 "범용 집필 지원 도구"와 **범위가 다르다.**

- 로어/파이프라인이 이 도구의 사용 사례 중 하나가 되는가
- 아니면 README가 남은 유산인가

확정 후 README를 이 로드맵에 맞춰 갱신한다.
